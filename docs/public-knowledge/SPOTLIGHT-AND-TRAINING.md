# Spotlight network + training + public knowledge

This document describes how Local Service Spotlight, niche Spotlight sites, courses, agent skills and public media should behave as one system.

## The graph

```
                         ┌─────────────────────┐
```

## Local Service Spotlight mothership

The mothership should make the whole system legible:

- what we believe;
- how the system works;
- canonical methods;
- public case studies;
- public people/entity pages;
- the Spotlight network;
- AI Builder path;
- installation/agent instructions;
- IF/THEN explorer;
- training catalog;
- local-service category entry points;
- public research/data;
- latest proof/results.

It should be the easiest place for a human to understand the network.

## Vertical Spotlight sites

A vertical is not a thin microsite. It is a category lens over the same system.

A good vertical has:

- category homepage;
- category people/entities;
- category case studies;
- category local SEO guides;
- category IF/THEN triggers;
- category service/query pages that are genuinely useful;
- category video/social proof;
- category operator/agency path;
- links to shared canonical methods.

The vertical should own category-specific queries while the mothership owns cross-category methods.

## Training

The training system should stop being an information warehouse.

Move durable public knowledge to public canonical pages.

Use Skool for:
- ordered paths;
- assignments;
- proof submissions;
- community;
- accountability;
- private support;
- certification;
- gated tools/resources;
- client/project access.

This lets a learner discover the method from Google/ChatGPT, join the community when they want structured implementation, and eventually execute for a real local-service business.

## The Builder journey

Publicly explain the ladder:

1. open/public learner;
2. candidate who ships proof;
3. funded apprentice;
4. Lighthouse builder;
5. client operator;
6. category/agency operator;
7. exceptional partner.

Specific operational access and client details can remain private.

The important public principle is:

> access increases with demonstrated proof, not with the volume of private requests.

## Relationships

A public relationship graph creates compounding authority.

For every public person/company relationship, link:

- the entity pages;
- the public evidence;
- the relevant event/podcast/case study;
- the topic discussed;
- related methods;
- related vertical/category;
- useful next actions.

Example relationship object:

```json
{
  "subject": "person-or-company-A",
  "predicate": "appeared_on",
  "object": "show-or-event-B",
  "evidence": "https://...",
  "date": "YYYY-MM-DD",
  "topics": ["local-seo", "ai-builders"]
}
```

## Local SEO delivery

Execution content should connect directly to sellable work.

For each local SEO method, expose:

- diagnosis;
- public checklist;
- proof/examples;
- category-specific implementation;
- what can be DIY;
- what requires access/expertise;
- measurement;
- next-step offer.

The public page should help even if the reader never buys. The execution offer is the faster/safer implementation path.

## Content Factory distribution

One credible source should produce a connected set of assets:

- canonical long-form page;
- evidence clips;
- short videos;
- social posts;
- images/diagrams;
- newsletter/email;
- vertical adaptations;
- training lesson;
- agent reference;
- IF/THEN trigger;
- internal linking updates.

The derivatives should strengthen the canonical entity/topic instead of competing with it.

## Agent collaboration

Agents should be able to answer four questions quickly:

1. What is the canonical public owner for this topic/entity?
2. What public evidence supports it?
3. What private source, if any, is required to execute the task?
4. Where should new evidence be written back?

The public catalog answers 1–2. Private operational registries answer 3–4 when authorization is required.

## What success looks like

A contractor searches Google or asks ChatGPT a real question.

They find a useful Spotlight answer supported by real proof.

That answer links to the relevant person, method, case study and next action.

A learner finds the same method, enters the Builder path, proves competence, and eventually executes it.

A team member or agent finds the same canonical object instead of rebuilding the explanation.

A new client result feeds back into the proof set and improves the public page.

That is the flywheel.
