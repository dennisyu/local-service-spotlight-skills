# Data Pipeline Contract, Google Ads MAA

Canonical rules for how the `google-ads-analyzer` skill gets its data.

## Data source priority: MCP first, email fallback

**Primary, a Google Ads MCP connector.** Pull every dataset live via the MCP's
`search` tool (GAQL) against the client's CID, using
`shared/frameworks/gaql-query-pack.md`. The API returns correctly-labeled data,
including the Quality Score components, so on this path there is **no column
swap, no corrector, nothing to un-invert.** Read everything as-is.

**The MCP is read-only.** It reports; it cannot mutate the account. Bidding
changes, negatives, budget and bid moves all go through change scripts
(`google-ads-change-scripts`), never the MCP. Reading current state to target a
change is fine and encouraged.

**Fallback, the `maa-data-automation` email.** Use only when no MCP is
connected, the MCP is unavailable (e.g. its authorization lapsed), a query
fails, or the client's CID isn't confirmed. The email path is the original
pipeline: a Google Ads Script (generated by the `google-ads-script` skill)
running inside the client's account emails ten datasets weekly. The rest of
this document is the contract for that email format.

**Everything about the QS swap/corrector below applies to the EMAIL FALLBACK
ONLY. Never apply it to MCP data.**

## Email envelope (default convention, configurable)

- **From:** Google Ads Scripts (noreply)
- **To:** the inbox you designate for automation data (set in your script)
- **Subject:** `[MAA Data] {Account Name}, YYYY-MM-DD`
- **Label/filter:** `maa-data-automation` (any label works; the analyzer just
  needs to find the latest email for a given client)
- **Cadence:** weekly
- **Account-name source:** `AdsApp.currentAccount().getName()`, auto-detected,
  no manual config.

## The 10 markers

Each dataset is delimited by paired BEGIN/END markers. The order in the email
body matches the order below.

| # | Marker (begin) | Contents | Columns |
|---|---|---|---|
| 1 | `---BEGIN CAMPAIGN SUMMARY 30D---` | Campaign rollup, 30 days | Campaign, Status, Type, Bid Strategy, Cost, Impressions, Clicks, CTR, Avg CPC, Conversions, Cost/Conv, Search IS, Search IS Lost (Budget), Search IS Lost (Rank) |
| 2 | `---BEGIN CAMPAIGN SUMMARY 7D---` | Campaign rollup, 7 days | (same 14 columns) |
| 3 | `---BEGIN CONVERSION DETAIL 30D---` | Conversions by action name, per campaign, 30 days. Only rows where conversions > 0. | Campaign, Conversion Action, Conversions |
| 4 | `---BEGIN CONVERSION DETAIL 7D---` | Same, 7 days | (same 3 columns) |
| 5 | `---BEGIN KEYWORD REPORT 30D---` | Keyword data, enabled entities only, 30 days | Campaign, Ad Group, Keyword, Match Type, Quality Score, Expected CTR, Landing Page Exp, Ad Relevance, Cost, Impressions, Clicks, CTR, Avg CPC, Conversions, Cost/Conv |
| 6 | `---BEGIN KEYWORD REPORT 7D---` | Same, 7 days | (same 15 columns) |
| 7 | `---BEGIN SEARCH TERMS 30D---` | Search terms, top 100 by cost, 30 days | Campaign, Ad Group, Search Term, Cost, Impressions, Clicks, CTR, Conversions |
| 8 | `---BEGIN SEARCH TERMS 7D---` | Same, 7 days | (same 8 columns) |
| 9 | `---BEGIN AD REPORT 30D---` | Ad data incl. RSA headlines/descriptions (pipe-separated), ad strength, 30 days | Campaign, Ad Group, Ad Type, Headlines, Descriptions, Ad Strength, Impressions, Clicks, CTR, Cost, Conversions, Cost/Conv |
| 10 | `---BEGIN AD REPORT 7D---` | Same, 7 days | (same 12 columns) |

## Parsing notes

- CSV is embedded as text in the email body, not as attachments. Parse between
  marker pairs.
- Quoted fields: campaign/ad-group/keyword/search-term text is double-quoted to
  handle commas in names.
- RSA assets: headlines and descriptions are pipe-separated. Order is the API's
  return order, not the pin order.
- Bid strategy names: the script emits the API enum (e.g. `MAXIMIZE_CONVERSIONS`).
  The analyzer translates to the UI-facing name before any client-facing output.
- Null safety: quality fields emit `N/A` when the API returns null; non-RSA ad
  types emit empty strings for Headlines/Descriptions.
- Conversion Detail emits zero rows when there are no conversions in the window.
  Do not treat an empty section as a parse error.

## Known issue, Quality Score column inversion (email path only)

Some deployed versions of the collection script have a column-order bug in the
keyword query: the `Expected CTR` and `Ad Relevance` columns are swapped in the
CSV (Landing Page Experience is correct).

**Preferred fix, run the corrector at ingest (mechanical, not a judgment
call).** Right after saving the raw email data to a text file, run:

```
python3 shared/scripts/correct_qs_columns.py --infile path/to/{date}_email-data.txt
```

It writes `{date}_email-data_corrected.txt` next to the raw file with the two
columns un-swapped inside the KEYWORD REPORT 30D and 7D blocks. The correction
is positional, tightly anchored, and loss-less. **Then read the `_corrected.txt`
file and treat every column AS-LABELED. Do NOT swap again**, double-swapping
re-introduces the bug. Keep the raw file verbatim for the record.

**Manual fallback** (only if the corrector cannot run):

```
ad_relevance_value  = row["Expected CTR"]     # mislabeled in CSV
expected_ctr_value  = row["Ad Relevance"]     # mislabeled in CSV
lp_experience_value = row["Landing Page Exp"] # correct as labeled
```

**Sanity check every run (10 seconds):** record an anchor for each client, the
highest-spend scored keyword and its known corrected component reads, in the
client's notes. If this week's parse disagrees with the anchor, you did not
swap correctly. Fix it before writing a line.

**Do NOT print the swap in the report body.** It is an internal data-integrity
step. Apply it silently; report only corrected component names and directions.

Retire the swap only for accounts where a corrected script is confirmed
deployed, otherwise it re-inverts correctly-labeled data. On the MCP path this
whole section is moot: API fields arrive correctly labeled.

## Scope exclusions (both paths)

- **Local Services Ads (LSA) are out of scope.** LSA is a separate Google
  product with its own budget. The MCP path surfaces LSA campaigns
  (`advertising_channel_type = LOCAL_SERVICES`) even though the email script
  never carried them: keep LSA out of the Search headline math and out of the
  report entirely, same treatment as dormant campaigns. If a client wants LSA
  reported, it is a separate deliverable.
- **Dormant campaigns** ($0 spend in both 7D and 30D windows) are omitted
  entirely, not mentioned.
- **Campaign-level only.** Never analyze account-level aggregates as headlines.
